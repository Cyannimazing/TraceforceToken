# TraceForce Engine investigator agent

Every completed investigation requires actual **TraceForce Engine Investigator** review. Local Ollama is preferred when configured; optional Gemini handles unavailable or timed-out local inference, or runs directly when no local model is configured. A fresh request acquires and analyzes evidence deterministically, then profile **1.4.0** selects existing findings and caveats through validated references. The application restores canonical factual sentences; the model does not write the published main-report claims. Unavailable inference after any permitted fallback, invalid references, malformed output, cancellation or a deadline produces an error rather than a successful preset explanation. The result and evidence remain in page memory unless the visitor explicitly saves a local browser snapshot or downloads report JSON. There is no server report history or result recovery URL. Public visitors do not call the model directly or supply system prompts.

The question panel uses a short-lived signed context returned with a fresh scan. **Every accepted chat turn invokes genuine configured-provider inference**, including greetings, thanks, identity questions and clarification. Substantive replies use authenticated scan facts, the current message and bounded recent conversation; conversational prompts omit chain facts. Separate user and AI bubbles show messages after submission. Each request sends at most the last three completed exchanges (six messages, 1,000 characters each, 8 KiB total). History is untrusted context, never blockchain evidence. Conversation remains in browser/request memory and is excluded from snapshots, downloads and server storage. Restored snapshots need a fresh scan for active chat.

The named Ollama model is **`traceforce-investigator`**, built from **`qwen3:4b-instruct-2507-q4_K_M`** and the versioned `on-chain-investigator` profile. This is **instruction specialization**, not fine-tuning, a newly trained model, or proprietary base weights. The base model generates language; our profile, supplied evidence, structured output, validation, and runtime limits define its investigator role. The model does not acquire chain data, call tools, write to the database, or change the deterministic report.

The main-review context now chooses complete proofs jointly across the four investigation perspectives, with bounded deterministic shortlists. A dossier distinguishes retained events from supplied facts, explicit omissions, pinned candidate balances and source-reported metadata; transaction aliases preserve shared receipts. A genuine four-goal synthetic inference with the revised context passed in **67.506 seconds**, retaining all eight evidence records and four perspectives. This is one desktop selection/grounding check, not a general accuracy, speed or SWARM comparison. [Evaluation details](ai-evaluation.md#current-evidence-selection-upgrade-and-genuine-synthetic-check)

## Conversational questions and evidence constraints

Questions and recent history pass bounded input and English directive checks. Recognized off-topic, override, secret, tool/execution and trading-advice requests reject without inference. Capsule authentication restricts explicit targets to the current token and retained addresses/hashes. Ordinary greetings, thanks, help, identity questions and context-free clarification receive short, genuinely generated replies after authentication, with no supplied chain facts or evidence citations. Model failure returns an error, not a canned successful greeting. These checks do not prove resistance to all prompt injection, obfuscation or other languages.

All substantive funding, connection, accumulation, selling, coverage, methodology and unknown-fact answers invoke the configured AI provider. Selected canonical findings constrain allowed factual claims and citations; they are not returned as preset answer prose. The application restores complete original proof, including sale support. Missing findings stay unknown. The model must not invent absence from omitted facts, quote balances absent from its supplied context, or treat previous assistant text as evidence.

The model has no tools or fresh acquisition. For substantive answers, the prompt asks for two short sentences and one relevant caveat, with hard limits of 1,000/300 characters and four model aliases expanded to at most twelve complete references. Conversational replies use a separate short-answer schema with no citations and an empty caveat. Oldest history can be removed to preserve space for the current question and signed facts. Invalid output, unsupported citations, timeout or unavailable inference produces an honest error. Structural and lexical checks do not prove semantic accuracy.

## Explanation and authority

Profile **1.4.0** retains bounded, fully supported deterministic finding selection rather than a prefix of transactions. Before inference, the context builder tries selling, funding, accumulation and connections in that order, supplying at most one finding per category. Within a category, it prefers the fewest additional evidence records, then the smallest proof and a stable finding-ID order. Every selected finding's entire original evidence-ID set is retained; every selected sale includes its token/quote supporting flows. The default 12-record cap permits a minimal linked-selling proof with two sales and a prior link, which needs seven records. It does not guarantee that every larger finding fits.

Selection also enforces the unchanged 8,000-byte model-context budget and a 20-original-citation cap per finding. It never trims a proof to make a finding fit. Findings omitted because of category diversity, the evidence cap, byte budget or citation cap remain in the current-page deterministic report. Their reason counts and per-category supplied/omitted counts appear in both context and explanation limitations. If no finding fits, a small proof-complete overview sample can still be supplied; it creates no observation packet. Invalid retained sale support or an already truncated finding rejects before inference.

Full normalized records and exact decimal-string amounts remain unchanged in the in-memory report. The model receives compact, deduplicated source facts containing event kinds, block numbers/timestamps, directions, asset roles and sale protocol/pool/support aliases, alongside the selected finding statements and caveats. It receives no duplicate raw ledger. Normal requests write no acquisition archive or saved evidence. Token names and arbitrary visitor prompts are not sent. Context strings are data, never instructions.

Only the first four distinct general coverage warnings of at most 500 characters are supplied without truncation. Generated per-wallet funding-status lines are summarized by the exact status counts instead; omitted-warning counts include those lines, duplicates, overlength warnings and other unsupplied warnings. A bounded retrieval-failure cause remains available even when many wallet lines precede it. The structured schema is sent once through Ollama's `format` field or Gemini's `responseJsonSchema`; the user message contains a compact output-key hint instead of a duplicate schema. This keeps input bounded without raising the deadline or dropping retained evidence references.

Each request assigns **E1, E2, ...** aliases to supplied records, **F1, F2, ...** references to complete findings, and finding-local **C1, C2, ...** caveat references. The model reviews every supplied finding and its proof, returns one observation selector per finding, chooses one of that finding's caveats, and may reorder the observations. With findings present, it selects one or two F references for overview focus and leaves overview E references empty. Without findings, it selects up to two E references for a canonical evidence-kind summary; only an evidence-free context permits no overview references. Unknown, duplicate, omitted or mismatched references reject. No observation can substitute a shorter citation list.

The application restores the selected finding's canonical claim, exact indexed caveat, category and full proof. The published overview restores selected canonical statements or evidence-kind summaries, followed by exact coverage. Presentation may abbreviate source addresses and abstract raw accumulation units/timestamps; exact originals remain in the report. No model-authored claim, caveat, overview text or interpretation field is accepted by the strict selector schema. Canonical fork-specific IDs and transaction/block hashes stay out of model input; returned explanations use original IDs. Overview citations include complete selected evidence support and every observation's full proof, within the supplied context.

The model selects and reviews existing deterministic facts rather than rerunning investigation rules or authoring new factual prose. No eligible findings means no observations. Transfer records alone cannot enable an accumulation observation, and a single sale annotation does not create a deterministic linked-selling finding. Existing sale annotations and their complete supporting flows may still be overview evidence. A successful completed report still requires genuine inference and valid selectors; there is no successful fallback when the model fails.

Computed source facts give stable address-role labels, so repeated senders and recipients remain visibly identical. Canonical funding coverage separately reports complete, partial, unavailable and not-examined counts. Eligible wallets missing a coverage row remain not examined. Not examined means not checked; unavailable means history could not be retrieved. A completed bounded search is neither a positive funding event nor complete lifetime history. Native ETH funding and ERC-20 transfers remain distinct. The model cannot replace those meanings with a paraphrase or turn a possible infrastructure explanation into a published observed mechanism.

**Historical protocol:** profile 1.1.2 relied on instructions forbidding invented counts, magnitude judgments and exposed role labels. These prompt-only constraints did not reliably preserve meaning. Later 1.3.0 whole-finding references restored complete citations but still allowed free factual paraphrases, including the held shared-infrastructure claim recorded below.

Profile **1.2.0** introduced the still-used closed selection of request-local **L1, L2, ...** coverage references. The adapter supplies exact transfer-window coverage, exact funding-status counts and bounded original warnings as `coverageStatements`. The model may select at most three valid, unique references; unknown references and free limitation prose reject. References expand to canonical source statements, preserving hub attribution and unavailable versus not-examined counts. Profile 1.4.0 appends exact coverage to a canonically restored overview, not a model-written one.

One nonstreaming `/api/chat` request requires structured selector JSON, disables thinking, uses temperature zero, limits predicted tokens/context/threads, rejects redirects, and enforces byte/deadline limits. It supplies no tools or API key and requests unloading after generation. Main review returns at most two overview references, exactly one F/C selector per supplied finding (at most four), and up to three L references. The default output budget remains 800 tokens. Unexpected free-prose fields fail rather than being silently discarded or substituted. [Chat API](https://docs.ollama.com/api/chat), [structured outputs](https://docs.ollama.com/capabilities/structured-outputs)

`src/domain/investigations/explanation.ts` provides the shared pure completion-boundary validator. Public schema version remains **1**; profile 1.4.0 requires `grounding.mode="canonical-finding-selection"`, selected original finding/evidence IDs and each observation's finding ID/caveat index. Validation independently matches published overview/claim/caveat text to those canonical sources, checks exact finding/full-proof association, enforces at most one observation per category, and requires complete sale support. Citations must be unique supplied report IDs, and context counts must match. Empty overview citations are allowed only without evidence. Unfinished, malformed or tool-calling responses reject; errors stay sanitized. Earlier profiles remain readable as legacy commentary without acquiring canonical-grounding status.

Canonical correspondence constrains new main-report prose to existing facts; it does not independently verify acquisition completeness, rule correctness, provider claims or selection relevance. Generated natural chat and legacy main commentary can still misstate meaning despite valid citations. AI remains non-authoritative and cannot establish common ownership, coordinated intent, manipulation, lifetime-first funding, missing history, project safety or investment suitability. Any pinned candidate-balance metadata has its own source/block scope, not a live-balance or full-holder-census guarantee. Human review and broader evaluations remain necessary.

## Local-only operation and hosting

Leave `GEMINI_API_KEY` blank for local-only operation. Ollama's local API requires no paid API key. However, localhost alone does **not** prove local computation: Ollama can route cloud models through its local API. Explicit cloud model tags are rejected here, but custom aliases/proxies cannot be audited by this adapter. Disable cloud features on the **Ollama process** using `OLLAMA_NO_CLOUD=1` or its documented server setting, restart that runtime, and confirm its configuration. Setting this variable only in Next.js does not configure an already running Ollama server. Keep Ollama bound to loopback. [Authentication](https://docs.ollama.com/api/authentication), [local-only configuration](https://docs.ollama.com/faq#how-do-i-disable-ollama-cloud-features)

On Vercel, `127.0.0.1` refers to Vercel's execution environment, not the operator's PC or Hostinger VPS. Run the execution service on the separately configured host, beside private Ollama when using a local model. Optional Gemini credentials belong only in that protected engine's environment. The public API must use a deliberately configured protected streaming executor; Vercel cannot run inference against the operator's localhost. Database admission counters can limit requests without saving their reports or evidence. The Ollama adapter itself accepts loopback only and does not expose a remote unauthenticated model service.

CPU inference on a small VPS requires measured latency, memory, concurrency, and queue/backpressure checks. Scheduling/supervision, model health monitoring, throughput limits, production capacity, and model-quality benchmarks need separate deployment verification. Twelve records are a context ceiling, not a promise to include twelve or the entire report history. The interface retains full evidence, deterministic findings and explicit AI omission counts. Profile 1.4.0's synthetic fixtures verify selector binding, canonical text restoration, legacy compatibility, complete linked-selling proof and cancellation. They do not establish general model-selection quality or live funding/selling accuracy.
