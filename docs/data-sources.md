# TraceForce Engine data sources

Documentation reviewed: **2026-10-12**. Initial chain: **Base mainnet, chain ID 8453**.

TraceForce Engine implements fresh full-scope Base token crawls, bounded JSON-RPC acquisition with explicit fallback, optional paginated Alchemy token and native-funding discovery, optional Blockscout funding history, a local-evaluation SQD recipient index, GoPlus holder candidates/count context and contract checks, pinned RPC balances, and separate DEX Screener website/market metadata. Launch discovery remains planned. An available adapter describes code support; it does not establish configured credentials, endpoint health, complete history, or detection accuracy. Public content is maintained in [`src/content/data-sources.ts`](../src/content/data-sources.ts). Actual live checks appear in [provider verification](provider-verification.md); the review date here concerns documentation.

## Implemented evidence adapters

### Base JSON-RPC: blocks, contract reads, events, and receipts

The implemented adapter verifies chain ID 8453, pins a `finalized` block range, chunks token Transfer queries, validates successful receipt inclusion and canonical block hashes, and rechecks the final block. Operator-configured `BASE_RPC_URL` must use an approved HTTPS hostname. Public Base, PublicNode and dRPC endpoints can use this standard-method transport, but their actual method access differs. Plan-specific Alchemy/Infura endpoints use the same boundary. No provider URL is accepted from scan input. [Base connection information](https://docs.base.org/get-started/connect-to-base), [Base finality](https://docs.base.org/specifications/transactions/transaction-finality)

Optional `BASE_RPC_FALLBACK_URLS` configures at most two distinct approved endpoints, in order; it enables no automatic provider subscription. After a transient failure, recognized throttle, HTTP 403 or method-not-found (`-32601`), the collector can advance to an explicitly configured endpoint. Before replay, it verifies Base chain ID and the number/hash/time of every already-pinned range header. Each physical RPC read, handshake and retry consumes the same phase/total call budget; the canonical reserve and original range remain binding. Malformed evidence, wrong-chain/hash identity, cancellation and exhausted budgets never trigger integrity-error fallback. HTTPS, public-DNS checks, read-only methods, no redirects, deadlines and body caps apply to every endpoint. Public provider labels describe the scan-wide source set, not per-record independent corroboration.

Optional `BASE_LOG_RPC_URL` selects one separately validated endpoint for token-log discovery, leaving receipt/state reads on `BASE_RPC_URL` and its explicit alternatives. Core verifies that log source's chain and pinned range within the same call budget before requesting events. A log access failure leaves partial transfer coverage without disabling otherwise healthy state reads. Smaller chunks are attempted only for explicit log range/result-size or response-body limits, not generic access/network errors. PublicNode log access and dRPC state access have each worked in bounded checks; a successful method/range does not guarantee access to others. [Exact diagnostic scopes](provider-verification.md#independent-log-lane-and-known-positive-transfer)

One HTTP 403 from an actual query on that verified log lane can start a single recent-first pass over still-unvisited newer chunks. It neither retries nor shrinks the refused range, adds an endpoint or increases allocation. The next generic access/availability failure ends the pass. The refused bounds remain unknown and transfer coverage remains partial even when newer receipts verify; this recovery does not imply a complete history or launch window.

Configure `BASE_ALCHEMY_RPC_URL` with your private Base endpoint and explicitly select `BASE_TRANSFER_SOURCE=alchemy` and/or `BASE_FUNDING_SOURCE=alchemy` on the protected engine. Fully verified token receipts retain their complete matching ERC-20 log set. Partial pages, record/call limits and failures do not become complete coverage. Indexed query exhaustion cannot independently exclude omitted transactions, and this adapter does not acquire internal-transfer traces.

The full-scope request starts at Base block 0, avoiding unsupported assumptions about token deployment. Wider accepted log chunks reduce empty-history requests; paginated indexing avoids that block-range traversal. ### DEX Screener: source-reported token websites and market context

The optional website adapter requests only `https://api.dexscreener.com/token-pairs/v1/base/{contract}`. The documented pair schema includes `info.websites`. Returned entries must identify the Base chain and the exact requested **base-token** contract. A requested token appearing only as a pair's quote token is ignored because the pair's website metadata cannot safely be attributed to it. This conservative attribution is an implementation policy, not a website-ownership guarantee from the API. [DEX Screener API reference](https://docs.dexscreener.com/api/reference)

The lookup owns a five-second deadline, a 256 KiB decoded-body limit, and at most 100 pairs. The report retains up to five distinct credential-free HTTPS links and their matching pool contract addresses, with source and check time. Recognized 32-byte pool IDs are skipped with an explicit reason because this metadata contract retains only 20-byte pool addresses; an unsupported listing does not erase other usable listings. Redirects and arbitrary website fetches are disabled. The link policy rejects local/private-address syntax, reserved local suffixes, nondefault ports, controls, and embedded credentials; it does not verify that a project controls a public hostname or that visiting it is safe.

The same response also supplies a separate market snapshot. Matching Base/base-token pairs are ranked by greatest valid reported USD liquidity, then pair address and canonical row content to resolve ties deterministically. Price, market cap, liquidity, 24-hour volume/change and pair creation time all come from that selected row; values are not mixed across pools. Price retains its decimal string, approximate fiat metrics must be finite and bounded, and missing/invalid values remain null. Pair age is the selected pool's reported age, not token launch age. Website parsing failure does not erase otherwise valid market context, and a market field failure does not erase accepted website links.

`reported` means at least one accepted link; `not_listed` means a valid bounded response reported no accepted link; `unavailable` means the lookup failed or could not be validated. Reasons distinguish absent metadata from rejected unsafe links or result caps. Different links remain separate instead of selecting an invented official site. The UI must label them as source-reported with ownership unverified. Website metadata is separate from receipt-backed evidence and is excluded from the compact AI evidence context. A lookup failure does not turn into proof the project has no website.

Injected-response tests verify identity matching, deterministic single-pair selection, exact decimal prices, missing/invalid market fields, conflicting/deduplicated links, unsupported pool IDs, absent versus failed lookup, unsafe links, resource caps, cancellation, and stalled-body deadlines. These are fixture checks, not a live DEX Screener availability or metadata-correctness benchmark.

## Data authority and source disagreement

Canonical successful receipts and logs substantiate onchain events at an identified block hash. Indexers help find those events, while market aggregators add context. Neither a trusted provider name nor agreement between two websites independently proves ownership, intent, or safety.

Reports expose a References section with the token's BaseScan page, available fixed DEX Screener/GoPlus source endpoints and a link into the retained transaction ledger. Metadata links carry their recorded status/check time; the ledger exposes block/transaction identities, acquisition references and transaction explorer links. An explorer link does not identify the RPC provider used, and a provider link does not make source-reported counts, flags or websites verified chain facts. Opening an external API link can show newer source data; it does not replay the response used for the report.
