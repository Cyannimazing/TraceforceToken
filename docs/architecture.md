# TraceForge Engine architecture

Implementation reviewed: **2026-10-13**. Network: **Base mainnet, chain ID 8453**. The product is public and free without accounts, wallet connection, payment, or token ownership. The network registry currently enables only Base; an EVM address does not imply support for another chain. Historical verification below retains the versions and dates actually tested.

## Fresh results and visitor-controlled snapshots

Each scan acquires fresh data, analyzes it, exposes a deterministic evidence preview, obtains a required AI explanation, and streams one completed report to the current page. The preview cannot be saved, downloaded, shared as a completed report or used for chat. If AI fails or is cancelled, it remains explicitly incomplete. Public execution has no durable job, report lookup, server evidence archive, result deduplication, or server history. Closing the connection, restarting the engine, or exceeding a deadline loses that active result. A retry is a new acquisition.

The report lives in browser memory by default. Explicit Save stores the validated report in that browser/origin's IndexedDB. Saved snapshots are bounded to five reports and 20 MiB of serialized report data, with least-recently-opened eviction when a save exceeds either limit. Delete and Clear remove them; browser cleanup or storage denial can also make them unavailable. Snapshots carry their original data-through range and generation time. Opening a snapshot does not crawl or make it current.

Chat capsules and conversations are never included in snapshots. Questions on a restored snapshot require a fresh scan. Downloads are visitor-created files, separate from server persistence.

Database/provider credentials stay server-side. Domain validation is shared with the browser and imports no database or Node-specific APIs. Amounts remain decimal strings or bigint. Source-reported metadata does not gain chain verification by entering a capsule.

## Public request flow

New public reports use explicit `assessmentAuthority: swarm`, following the user's selected presentation policy. The primary score, verdict, category points, decision weights, market values and holder cohort come from one validated SWARM snapshot. Its graph and table share the same retained source rows, order and reported float shares; source totals and group counts retain SWARM's conventions and may differ from a filtered report cohort. Neither groups nor SWARM's “hands” identify people or establish common ownership. Separate independent TraceForge summaries partition pinned positive candidates into wallets, contracts, unclassified, pool/burn and otherwise unrepresented rows; unread balances and unpinned source totals remain separate. Local exclusion roles require retained authenticated pools or exact burn addresses, never contract code alone.

1. A page GET initializes a signed HttpOnly anonymous visitor cookie. POST /api/investigations checks origin and the cookie, consumes one of 30 shared scan/question requests in a per-visitor 30-second window, then validates a 2 KiB JSON body and a canonical Base contract. `scope` defaults to `full`: token acquisition requests Base block 0 through the pinned finalized block. Explicit `window` scope uses 100–20,000 recent blocks (default 20,000). There is no visitor-selectable wallet count or 50-wallet ceiling: all discovered participants are eligible, with provider/time/acquisition limits disclosed as coverage gaps.
2. Before execution the server acquires one temporary distributed scan lease for that visitor. Separate browsers have independent opaque HMAC keys, including localhost; tabs share their browser's identity. Only counters/lease metadata are stored, never parameters or report IDs. The lease releases on stream completion, cancellation, disconnect, error or the outer 300-second deadline; 330-second expiry recovers a lost process, and stale releases cannot clear replacements.
3. Local non-Vercel execution invokes the collector directly. Vercel requires a configured protected HTTPS engine. Next.js forwards only validated parameters and private infrastructure authorization.
4. Acquisition pins finalized block identities, verifies bounded token transfers, performs bounded pool authentication, discovers holder candidates, investigates funding, enriches supported trades, and then reads pinned balances. Optional SWARM and enrichment requests overlap this work; their address candidates require the same independent pinned-state verification. It returns explicit coverage; pure analysis creates findings and a transient report ID.
5. After the validated preview, one shared AI slot performs required review of supplied findings and complete proof. Profile **1.6.0** selects canonical finding/caveat references and writes one/two short sentences in `summary.text` about at most two selected structured decision reasons. The exact action, verdict, source and reason metadata remain canonical; the generated prose carries `summary.grounding.mode="source-grounded-prose"` and repeated source/numeric/unit/direct-claim checks. Findings and citations retain their original canonical restoration. SWARM remains the primary authority for new SWARM-led reports, with independent blockchain observations separate. Missing source data remains unavailable; missing or invalid model text is an error, not a preset successful explanation. Legacy 1.5 summaries keep their canonical-only packet, and older saved profiles retain their original requirements. Prose guards do not establish broad semantic correctness, acquisition completeness or source accuracy.
6. NDJSON progress and an optional analysis frame lead to one terminal report or error. The report is bounded to 8 MiB and the stream to 16 MiB. Browser and proxy validate stream envelopes and report content; an initial HTTP 200 is not a successful terminal report. The loader presents one readable phase, indeterminate progress and elapsed time without treating a phase label as a completion percentage. No polling/saved-job API participates.
7. POST /api/questions uses the same visitor's 30-request/30-second counter, then accepts the current question, signed capsule and optional recent conversation (six messages, 1,000 characters each, 8 KiB combined). English topic/directive checks reject recognized off-topic, override, secret, execution, personal-allocation and price-prediction requests before inference. Ordinary questions about buying, selling, risk and the report’s practical meaning reach the model with the current assessment and its limitations. Accepted turns share engine capacity. Signed-context validation restricts explicit targets to the current token and retained facts. Every accepted turn invokes the configured AI provider, including greetings, thanks, help and clarification. Substantive answers use authenticated compact facts and selected complete finding proofs; social prompts omit chain facts. Recent conversation is quoted untrusted context; previous assistant prose is not evidence. Model failure is an error, never a preset successful answer. Conversations are never persisted.

Burst admission precedes validation/execution. A later capacity, provider, model or context failure still consumes one short-window request; it does not guarantee a completed result. The old five-per-hour repository is retained only for legacy tests and has no public caller. Browser identities can be recreated, so perimeter protections remain necessary for hosted DDoS defense.

Signed packets authenticate report-derived facts; they do not establish complete history or semantic truth of a generated chat answer. Profile 1.6.0 adds a short generated explanation grounded in selected structured decision reasons; canonical facts, source authority and complete evidence references remain separately validated. Legacy 1.5.0 selects canonical text only. Source/rule correctness, selection quality and generated semantics remain separate concerns. Ordinary score, verdict, holder and market questions follow the same explicit primary authority as the report. Explicitly independent/pinned/Alchemy questions use the separately supplied local facts and coverage. Compact SWARM context has priority within the existing combined 4 KiB assessment-context budget, preserving the independent event/proof budget and 32 KiB capsule envelope. If primary source context is absent or omitted, the authority marker remains SWARM and a missing score is not replaced with local points. Legacy absent-flag reports retain local behavior. Disagreement is not proof that either policy is more accurate. English heuristics are not a complete prompt-injection defense. The historical 04:36:29 UTC stream verification predates these policies; see [verification scope](reliability.md). Hosted operation remains unverified.

Main-review context selects complete finding portfolios jointly from at most eight candidates per perspective. It favors represented perspectives before category priority, story-specific findings and compact shared proofs. It never truncates a finding's support to fit. The compact dossier discloses retained event counts, supplied/omitted/no-retained-finding states and source authority; transaction aliases preserve which proof events share a receipt. The existing byte/record/token budgets and canonical restoration remain binding. Local main review allows one summary-only regeneration after complete selector/citation validation when generated prose alone fails semantic grounding; it retains the selected reasons, model and original request deadline. No cloud, citation, JSON or transport failure enters this correction. Shortlisting and context limits can omit findings, and more context can increase CPU latency. See [the bounded synthetic inference](ai-evaluation.md#current-evidence-selection-upgrade-and-genuine-synthetic-check).

Separately, deterministic analysis limits detailed individual token-transfer findings to 128 and discloses the exact number of transfers without an individual finding/timeline summary. All acquired evidence, candidate wallets, graph connections, linked groups and their complete proofs remain in the report. This bounds duplicate narration without changing acquisition limits or treating omitted summaries as missing evidence. The existing report/stream byte checks still apply; this presentation cap is not a universal size guarantee. See [the dense-token regression](reliability.md#dense-token-response-failure-and-bounded-narration--2026-10-14).

## Hybrid sources and authority

TraceForge independently acquires and analyzes blockchain evidence while displaying SWARM as the chosen primary assessment. Alchemy's optional indexes discover candidates; canonical RPC receipts, transactions, block identities, account state and exact balances establish the retained local on-chain facts. GoPlus contract flags, DEX Screener metadata and all SWARM assessment/graph/market fields stay source-reported. An LLM explains the supplied sources and selects supported reasons; it does not supply missing measurements, independently validate a source verdict or determine ownership.

The SWARM adapter starts one fresh `POST /api/scan` job, follows `/api/events`, and reads `/api/result` under a bounded deadline. It validates Base/token identity and bounded response shape, and assesses timing against the source HTTP clock and measured request duration. A reliably stale result rejects; missing or inconsistent source clocks retain only explicitly unverified timing context. New public reports display that validated snapshot's main score, verdict, category points, weights, market header and holder graph/table together, retaining its reported source time. The source graph is bounded to 256 holder rows, 2,048 links and 256 clusters; omitted rows/links remain disclosed. A source pool identifier may be a 20-byte EVM address or 32-byte pool ID. It is source context, never authorization for an RPC contract call. SWARM does not mutate the independent local category ledger, evidence or pinned holder denominator. Cached token/history lookup, Council, replay, DNA, wallet X-ray, radar, cabals, feeds and share-card endpoints are not integrated. The local Deployer DNA panel describes retained creator evidence for this scan, not complete token history.

Configured Bubblemaps and Nansen adapters contribute bounded source-reported holder/context candidates; Bubblemaps may also supply reported transfer relationships. The request-owned service merges optional address leads, deduplicates them and offers at most 512 to the existing collector. Excess or unverified leads remain gaps, never verified balances, receipt-backed links or proof of common ownership. Labels and relationship reports retain their external authority even when their addresses also receive an RPC balance read. Agreement between services does not establish independent corroboration or calibrated confidence.

Source timeout, access denial, throttling, stale identity or invalid output is contained to that source, with a validated availability reason and human-readable disclosure. Independent acquisition can still complete, but an unavailable primary SWARM assessment remains visibly unavailable: null score, INSUFFICIENT summary and no local score/weight/cohort fallback. Parent cancellation and local evidence-integrity failures remain terminal; sources do not relax the collector's budgets or final canonical check. Requests disclose the public token and sometimes candidate addresses upstream, where providers may retain their own data or jobs. TraceForge's no-server-history policy cannot delete or govern those external records. See [security boundaries](security.md#optional-source-access-and-privacy).

`BUBBLEMAPS_API_KEY` and `NANSEN_API_KEY` are optional engine-only credentials; `ENRICHMENT_TIMEOUT_MS` defaults to 12,000 with a maximum of 30,000. Keys establish authenticated access, not commercial or redistribution permission. Operators must confirm suitable service terms before enabling them. Arkham remains `rights-required`, RugCheck remains `unsupported-chain` for this Base implementation, and no Honeypot.is runtime adapter is enabled because its published API terms restrict third-party and competing use. Those capabilities are not silently simulated.

## Execution and deployment boundaries

One engine process admits at most three active operations, permitting acquisition overlap, and runs one inference at a time. Other admitted operations wait in bounded memory. Questions share the active/inference limits. These are per-process controls; multiple engines require an explicit capacity design.

The scan deadline is 270 seconds including AI waiting. Provider collection and AI each have separate 120-second budgets. A collection deadline raises `ProviderDeadlineError`, preserving distinct public retry/recent-window guidance even when the outer scan signal has not expired. The Next.js remote scan proxy owns a 285-second deadline; its route declares maxDuration 300. Questions use a 135-second engine budget, 140-second remote proxy budget, and route maxDuration 150. Host limits still need verification.

The planned split is Next.js on Vercel, admission-only MySQL, and a protected VPS Node engine beside loopback-only Ollama. MySQL can use a separate host or the [optional one-VPS cohosting profile](../deploy/linux/cohost/README.md); cohosting changes resource allocation, not module/data boundaries. Only Next.js receives admission database credentials. Linux units/resource ceilings are prepared, not installed or benchmarked on Hostinger. The cohosting profile requires verified MySQL TLS and a reviewed Vercel egress/network design before opening database access.

## RPC recovery and indexed funding

### Fresh full crawls and indexed discovery

Full scope searches from Base genesis rather than inferring deployment from pool metadata or historical code probes. `coverage.transferCrawl` records scope, acquisition source and only completely processed ranges. Shared analyzer/browser/proxy validation rejects a `complete` full crawl with missing, overlapping or out-of-range coverage. A scan can finish with explicitly partial acquisition; full intent alone never upgrades its coverage. Legacy direct collector callers without scope retain their explicit lookback behavior, while public schema parsing always supplies scope.

The optional fixed `BASE_ALCHEMY_RPC_URL` lane supports explicit `BASE_TRANSFER_SOURCE=alchemy` and `BASE_FUNDING_SOURCE=alchemy`. The token reader paginates ERC-20 transaction candidates across the requested range in up to 1,000-row pages (`maxCount: 0x3e8`), following [Alchemy's pagination behavior](https://www.alchemy.com/docs/reference/transfers-api-quickstart#pagination); the funding reader retains 100-row pages for top-level inbound native candidates for each eligible wallet. Neither accepts indexed decimal amounts as evidence. Core verifies the indexed lane's Base identity and pinned range headers under the shared call budget, then validates candidates against canonical state-RPC receipts/transactions. Every token receipt contributes all valid token Transfer logs, preventing a source row from hiding sibling flows. Cursors stay on their original fixed source, with bounded pages, loop/identity/order checks and partial coverage on availability or capacity failure. Cursor exhaustion describes the indexed query, not independent proof against index omissions. Internal native transfers remain unexamined.

The RPC-log path accepts configured chunks up to 10,000,000 blocks (configuration default 1,000,000), halving only explicit range/result/body limits. This saves reads across accepted empty historical ranges; plan limits can still prevent a useful full crawl. Independent configured hostnames are resolved concurrently and each hostname once per preflight, preserving fallback priority and rejecting prohibited destinations before HTTP acquisition. Token metadata already overlaps chain collection. These remove avoidable sequential work without a persistent cache or relaxed evidence checks.

For a full scan with a receipt-backed direct creator and the configured Alchemy funding lane, acquisition first queries that creator's outbound external-native transactions from genesis through the pinned block. It uses at most two 100-item pages on the fixed index source; index authentication, pages, canonical transactions, successful receipts, block identities and historical recipient code share the existing funding and total call limits. Retained funding recipients must belong to the already classified pinned EOA cohort. Pages commit atomically; failed or unfinished pages cannot claim completeness. This small source query runs before variable recipient histories and preserves the balance, trade and final canonical allocations.

Optional `coverage.creatorFunding` records its exact creator, cohort, range, scope, retained evidence and pagination status. It never changes `coverage.funding` or claims complete recipient histories. Runtime analysis and report validation tie it to the actual direct deployment and pinned EOA classifications. A completed genesis token crawl plus authenticated initial liquidity and a completed creator query covering every scored wallet can assess the narrow direct-creator pre-liquidity Insider metric, even when unrelated inbound histories remain partial. Internal funding, indirect relationships and index omissions remain outside that claim; incomplete creator coverage earns no favorable absence credits.

For a fully completed full crawl, earliest-observed accumulation starts at the first retained token Transfer timestamp, not the genesis timestamp. It remains a 600-second observed-flow rule, not market-launch/sniper or purchase proof. Partial transfer history keeps those wallet labels unknown. Operator scripts can inspect the external reference and verify a full crawl without persisting reports: `npm run inspect:swarm` and `npm run verify:full`.

An optional, single `BASE_LOG_RPC_URL` gives token-log discovery its own approved endpoint while metadata, receipts, funding verification and balances stay on the state RPC lane. It is never inferred from fallback order. Before its first log query, core verifies Base chain 8453 and both already-pinned range headers through that lane, counting every read against the same allocation and preserving the final canonical reserve. State-provider advancement cannot move the log lane. A log access failure leaves transfer coverage partial without latching a healthy state lane as throttled. Only an explicit log range/result-size or decoded-body limit permits smaller chunks; unknown availability/access failures do not trigger repeated range shrinking.

If that verified independent lane refuses one queried range with HTTP 403, the range remains an explicit gap and core makes one recent-first pass through still-unvisited newer chunks. It uses the same endpoint and allocation, without retrying or shrinking the refused range. A subsequent generic access/availability failure stops the pass. Receipt/header access failures and unverified log-source handshakes cannot trigger it. Even if newer evidence is retained, transfer coverage stays partial and cannot establish launch or complete early accumulation.

The operator sets one primary `BASE_RPC_URL` and optionally up to two distinct `BASE_RPC_FALLBACK_URLS`. Configuration and bounded DNS preflight validate all endpoints. Transiently unresolvable destinations are omitted; prohibited/private destinations reject. Transport performs one HTTP read per RPC invocation. Core orchestration owns the counted retry and one-way endpoint advancement after transient/throttle failures or explicitly recoverable HTTP 403/method-not-found responses. A new endpoint must return Base chain 8453 and matching number/hash/time for every already-pinned range header before replay. Handshakes consume the same phase/total call budget and cannot borrow the reserved final check. If a transfer-phase throttle could not fit recovery, the funding boundary can make one explicit next-endpoint attempt from its new allocation, only when the entire handshake plus a funding read fit. It clears the RPC throttle only after verification succeeds; transfer coverage remains partial. Integrity errors and cancellation never select another source. Public labels describe the scan-wide source set, not independent corroboration or exact per-response lineage.

`BASE_FUNDING_SOURCE` defaults to `rpc`; explicit `sqd-public-testing` enables `sqd-funding.ts` through the server collector. It validates the entire returned page's header/transaction structure and continuity, then anchors its first and last headers through RPC. Within that anchored page, each block stages its events and recipient exclusions until its required candidate checks succeed. Retained funding requires exact RPC transaction/successful-receipt inclusion, a canonical candidate header, and empty recipient code at both historical and pinned end blocks.

Only a fully verified block commits evidence and extends searched bounds. A later availability/budget failure preserves the completed prefix; its failed block contributes no events, exclusions or coverage. An SQD request's own timeout is a recoverable `UpstreamFailure`; if no block completed, remaining budget and throttle state can permit the bounded native RPC prefix. Parent scan cancellation or deadline preserves its exact abort reason and remains terminal, as do integrity failures. `complete` means the exact declared recipient-filtered indexed window was searched, not that index omissions, internal transfers or lifetime-first funding were ruled out. No qualifying candidate does not establish EOA identity or independently prove no funding.

## Evidence and feature scope

After bounded destination validation, one DEX Screener metadata lookup overlaps the chain acquisition under the same provider deadline and cancellation. Metadata unavailability remains explicit partial context; chain failure cancels the metadata task. This adds no cache, retries or persistence. The current local log chunk is 1,000 blocks rather than the former ten: larger accepted chunks reduce request allocation wasted on empty ranges, but provider range/rate/body limits and partial transfer coverage remain.

Reports expose funding/transfer relationships, groups, earliest-observed accumulation, supported selling evidence, a graph, timeline, and citations. Acquisition prioritizes the funding investigation within shared call and deadline limits:

1. After metadata, token-transfer discovery and receipt verification receive one third of the remaining call capacity, excluding the reserved final canonical call. An exhausted allocation leaves transfer coverage partial and preserves capacity for funding and later phases.
2. A bounded infrastructure pass authenticates selected and observed pool candidates and attempts pinned V2 reserves/direct deployment attribution before funding candidates are chosen. With a configured Blockscout key, bounded PRO holder pages add candidates. Otherwise one fixed GoPlus Base token-security request adds its documented Top10 candidates, reported holder count and selected source-reported checks. Holder discovery makes no balance reads, consumes the shared call budget and remains independent of RPC throttling. Observed and indexed participants are merged; zero and already known hubs are excluded from funding candidates.
3. Native funding is investigated after that infrastructure pass and pinned code/nonce reads, before trade enrichment or holder balance reads. The funding phase has its own bounded allocation, so priority does not guarantee complete history or examination of every candidate.
4. Supported trade enrichment follows funding, checking initial-liquidity candidates and each eligible wallet's first positive receipt before repeated trades, chronological within each tier. It uses remaining optional calls after reserving all known and receipt-backed candidate balance reads plus the final canonical call, without the former redundant half-cap. Proof requirements remain unchanged. Newly authenticated infrastructure is removed from funding candidates and coverage, and funding observations directed to it are deleted; examined counts are recalculated consistently. Token participants first revealed by supporting sale receipts receive explicit not_examined funding coverage rather than an implied search.
5. A separate holder balance phase reuses the retained discovery result, adds those late token participants as pending candidates, validates token, block and supply identity, and reads only candidates permitted by the remaining budget. It does not rediscover pages. If the configured fixed Alchemy lane has already authenticated Base and the pinned range, this phase uses at most four concurrent read-only balance calls there. Otherwise it retains serial state-RPC reads. The concurrent lane performs no endpoint recovery or hidden retries; every physical request consumes the shared allocation, with the exit-quote/final-canonical reserves protected. In-flight calls settle before terminal integrity errors are propagated. A recognized throttle stops subsequent batches; failed reads remain unavailable and unattempted reads remain not examined, never zero. An actual holder-index throttle remains binding; an earlier RPC-only discovery deferral does not stay sticky after verified RPC recovery. Focused fixtures cover this distinction, and the historical 06:39 live workflow verified all 70 retained candidates after recovery without claiming indexed discovery or a census.
6. The reserved canonical end-block recheck must still succeed before a dataset is returned.

If discovered balance candidates exceed remaining physical-call capacity, classification receives up to one eighth of that remaining capacity, capped at 50 calls; funding then receives the same bounded share of its own remaining capacity. This dense-cohort exception avoids reserving more balance reads than the entire budget and thereby starving the earlier investigation phases. It does not remove candidates or guarantee that every phase acquires evidence. Examination order puts the verified creator first, then indexed/source-reported holder leads, then other retained participants; all still require the same pinned reads and canonical proofs. The report header labels the full count as Addresses discovered. Classification, funding and balance coverage separately disclose what was actually examined.

Without optional funding indexing, one bounded contiguous oldest prefix of full blocks is searched for all eligible candidates. This path can also recover an SQD attempt that completed no block, when remaining budget and throttle state permit. Only fully verified blocks extend coverage or contribute their staged funding observations. Recipient code is checked lazily after a positive-value inbound transaction has a successful matching receipt, at both the pinned end block and the transaction block. A recipient identified as a contract or delegated account at the pinned end is excluded from this adapter's funding scope. Search coverage is not verified EOA identity: candidates with no qualifying inbound observation may have no code read at all. Precise searched bounds are retained; internal transfers and lifetime-first funding remain unexamined.

Sale support covers authenticated single-pool Uniswap v2/v3 paths with reconciled direct token/quote flows. V2 pool authentication precedes trade classification and final analysis, so a recognized pool does not connect its ordinary buyers into a wallet group. Purchases are optional annotations on their actual token transfers; initial V2 liquidity requires a successful authenticated Mint receipt with both deposits and the minimum-liquidity lock. Native-funded buys require the official router, exact transaction value and a matching WETH Deposit. Unsupported routes remain unclassified. Outgoing transfers alone are not sales or purchases.

Indexed candidate discovery can lag or omit historical holders; GoPlus's Top10 response is not a census or an application wallet cap. Failed or unreached balance reads remain null. The compact holder table ranks positive verified EOA candidates. Its presentation-only Float subtracts pinned authenticated pool and burn balances, then known contract balances at the same block, matching the reference's wallet table convention. Default wallet bubbles use these exact rows, denominator and rounded percentages. Contract balances stay visible in a separate section and in the graph's All addresses view, concentration and price-impact assessment. Unverified account types appear separately; missing account classification, eligible balances or pool balances causes an explicitly labeled total-supply fallback. The table never classifies a contract as a pool or locker merely because it has code. `holder-table-distribution.ts` does not mutate the report or `report-distribution.ts`, whose broader denominator remains in risk analysis. Neither population identifies human owners or proves circulating supply. Creator labels distinguish direct deployment proof from GoPlus attribution; contract checks remain source reports. Market context remains separately sourced from DEX Screener.

The pure `report-assessment.ts` module retains a separate independent local assessment without acquisition or persistence. It remains the primary presentation only for explicit TraceForge or legacy absent-flag reports. Category weights are Swarm 30, Fresh 20, Insiders 15, Concentration 15, Snipers 10 and Dev 10. Higher points mean lower measured risk under disclosed local curves. Missing measurements remain null and cannot earn favorable points. These calculations do not reproduce SWARM's private model or establish calibrated outcome probabilities.

Assessment version 1.4.0 retains the category curves introduced in 1.3.0. It calculates positive credits using exact decimal arithmetic in `report-category-score.ts`: weight × max(0, 1 − measured risk percentage / local saturation percentage), rounded to one decimal. Saturations are respectively 50%, 100%, 30%, 50%, 25% and 40%. The ledger sums integer tenths before the ring rounds to an integer. With complete account classification, holding metrics share the Top holders EOA cohort and its exact Float; excluded contract holdings retain separate concentration and hypothetical-sale warnings. Otherwise the explicitly labeled broader eligible-address basis applies. Fresh scoring excludes the attributed creator, whose Fresh badge remains visible and whose holdings have a separate Dev category. Insiders require completed declared genesis token/funding searches. Sniper credits require supported entry classification relative to the same authenticated initial-liquidity pool; unsupported routes or another venue cannot establish a favorable absence. Dev currently measures the attributed creator's pinned holding, not exhaustive creator-funded holdings.

Pinned authenticated V2 reserves support an explicitly hypothetical no-fee constant-product price-impact model. A modeled drop of at least 50% or an attributed GoPlus hard warning produces DANGER/AVOID. Creator holdings of at least 10% and locally defined thin-liquidity warnings produce RISKY/CAUTION with the disclosed soft cap of 59; a hard warning takes precedence. Previously linked selling retains its proof without pretending it measures price impact. Unknown measurements remain null and earn no favorable credits. A numeric zero credit is not a measured absence of risk. The ring marks the rounded policy-adjusted subtotal PARTIAL until all categories are assessed, while verdict completeness also requires the disclosed market and contract checks. A fully assessed clean set can produce OK; observed concerns produce REVIEW, and incomplete clean-looking evidence produces INSUFFICIENT. Neither OK nor completeness is a full audit or safety guarantee. Rule proof deductions reflect the category ledger and never stack additional losses. The separate pure `traceforce-judge-1.0.0` model retains normalized local rule weights for validation and compatibility; the normal report hides raw decision masses, model receipts and debug JSON. ## AI provider execution

`src/agents/model-transport.ts` owns fixed-destination local/OpenRouter/Gemini JSON transport; `src/agents/inference.ts` executes the selected providers.
