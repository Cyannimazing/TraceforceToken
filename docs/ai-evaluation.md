# Investigator evaluation plan

Status: **proposed; the release gates below have not been run or passed**. This document separates a real inference measurement, automated output validation, and review of what the generated sentences mean. No model is assumed accurate because it returns JSON or uses valid evidence IDs.

The main-report investigator selects existing deterministic findings and caveats; profile 1.4.0 restores the published factual sentences and complete proofs from the report. Chat separately generates bounded prose. Neither path establishes new findings, ownership, trading intent, current holdings, safety, or investment suitability. Model selection and prompt specialization are not fine-tuning. Changing the model requires another evaluation; neither a newer checkpoint nor a smaller download guarantees fewer errors.

The current uncertainty-focused instructions keep that same 1.4.0 selection and validation contract. The trace engine owns acquired evidence, balance calculations and rule-based flags; the local LLM reviews supplied findings and prioritizes missing coverage, ambiguous relationships and inference limits when choosing their order and canonical caveats. It still reviews each supplied finding with its proof, rather than receiving isolated unknowns that could invite guesses. The report identifies both roles and the actual model, with supplied and omitted evidence counts in its review receipt. This prompt refinement has automated grounding regression coverage; the earlier genuine-inference measurements below predate it and do not verify its selection quality or latency. Recreate the installed alias with `npm run ai:setup` after a Modelfile change; application calls also send the reviewed system instructions explicitly.

An adjacent **Investigative leads** disclosure is derived by deterministic code from the acquired report, separately from LLM output. It prioritizes shared funding sources, incomplete funding for the reported creator or important pinned holders, prior-linked sales, direct token transfers and the earliest retained supported buy after authenticated initial pool liquidity. Each target shows the observed basis, actual wallet addresses, complete retained proof IDs when present, and a specific next check. Missing funding searches use snapshot/source-context and coverage state with no invented transaction citation. Three leads appear when opened, with at most six available. These are proposed follow-up checks, not newly acquired upstream funding, traced proceeds, human identities or proof of common ownership. The current collector does not recursively expand a discovered funder's upstream funding or trace quote proceeds after selling; those require a separate bounded acquisition implementation and verification.

## Candidate models and resource limits

The currently selected base is `qwen3:4b-instruct-2507-q4_K_M`: approximately 2.5 GB of model data, 4.02B parameters, Q4_K_M. Qwen describes Instruct-2507 as non-thinking only and reports improved instruction following over the original hybrid Qwen3-4B. Those published results do not measure our quantized investigator, its prompt, or a 2-vCPU host. [Ollama tag](https://ollama.com/library/qwen3:4b-instruct-2507-q4_K_M), [Qwen model card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)

If the measured 4B CPU latency is unacceptable, `qwen3.5:2b-q4_K_M` is a smaller candidate at 1.9 GB. Its official card says non-thinking is the default for 2B, while both modes remain supported. Its published non-thinking instruction-following result is lower than 4B-2507's; this does not predict our exact task, but prevents treating smaller weights as an accuracy improvement. Test it independently with the same retained cases. [Ollama tag](https://ollama.com/library/qwen3.5:2b-q4_K_M), [Qwen model card](https://huggingface.co/Qwen/Qwen3.5-2B)

An optional older instruction-tuned comparison is `gemma2:2b-instruct-q4_K_M`, 1.7 GB and 2.61B parameters. A different model family also needs its own template and structured-output checks. It has not been benchmarked here. [Ollama tag](https://ollama.com/library/gemma2:2b-instruct-q4_K_M), [Google model card](https://huggingface.co/google/gemma-2-2b-it)

Download size is not total resident RAM. Context, inference runtime, OS, Next.js, worker and database also consume memory. Qwen warns that longer context can cause out-of-memory errors. Ollama documents that parallel requests increase context allocation. Start with one inference slot, one loaded model, a bounded context and two inference threads, then measure the actual target host. These settings are not proof of available capacity or CPU speed. [Qwen context warning](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507), [Ollama concurrency documentation](https://docs.ollama.com/faq#how-does-ollama-handle-concurrent-requests)

## One retained-data CPU measurement

Run this explicitly against an existing acquisition dataset, after the reviewed model is installed and configured:

```sh
npm run ai:benchmark -- --dataset=.artifacts/<retained-dataset>.json
```

The script performs one genuine inference through the production analyzer and investigator adapter. It reads a bounded JSON file under `.artifacts`, forces `num_gpu: 0` and `num_thread: 2`, and calls only the configured loopback Ollama endpoints. It does not connect to the database, acquire fresh chain data, download models, create models, or update application reports. `--help` performs no inference.

The resulting `.artifacts/ai-benchmark-*.json` contains the input hash, model identity/digest when available, profile version, configured budgets, exact model request, bounded response, retained evidence/report, explanation if structurally valid, API timing/token counts, and matching `/api/ps` samples. Raw request/response content remains local for audit; review it before sharing the artifact.

CPU verification has three possible results: zero VRAM observed for the matching loaded model during inference, GPU allocation observed, or no usable loaded-model sample. The third result remains unknown. A requested zero-GPU setting alone is not an observation of runtime placement. Polling can miss a short run or a transient allocation. `/api/ps` model allocation is not peak process RSS. API durations are reported in nanoseconds; generated tokens per second uses generation duration only, while elapsed time includes the adapter request and validation.

The script records OS CPU models, logical CPU availability and total/free RAM. Running two inference threads on a larger desktop does not reproduce a 2-vCPU cap; reading 8 GB of total RAM does not establish available memory under application load. A deployment capacity decision additionally needs measurement on the target host, peak model/runtime memory, swap activity, simultaneous application load, cold/warm runs, timeouts, queue growth and recovery. A local GPU result is not a CPU result.

The artifact reports `structurally_valid` or `failed`, with semantic review always **pending**. It never marks accuracy passed. Inspect the generated report and the exact supplied context before accepting its prose. An execution failure, invalid output, invalid citations and a factual error are different outcomes and must remain separate.

## Proposed semantic fixture matrix

### Current evidence-selection upgrade and genuine synthetic check

The 2026-10-12 retrieval update preserves profile **1.4.0**, the installed Qwen3 4B instruction model, two CPU threads, zero requested GPU layers, one inference and the existing 12-record/8,000-byte/4,096-runtime-token/800-output-token/120-second caps. It jointly selects whole finding proofs across the four perspectives. Each category has a deterministic shortlist of at most eight cheap/story-specific candidates; at most 9^4 portfolios are considered. Selection favors category coverage, then the declared category priority and shared-source/component findings, proof reuse and byte size. It is bounded selection, not a globally optimal search across every retained finding. A regression case retains all four perspectives through overlapping support where the earlier greedy choice crowded one out.

A compact dossier distinguishes retained event counts from supplied evidence, marks each perspective supplied/omitted/no-retained-finding, and separates receipt-backed observations, pinned candidate balances and source-reported GoPlus/DEX context. Receipt aliases preserve transaction grouping without repeating full hashes. Source agreement does not imply independent corroboration. These improve the evidence presented to the same model; they do not create more capable base weights or establish superiority over SWARM's undisclosed model.

## Proposed acceptance and reporting

For an initial integration check, retain one genuine CPU run and review its prose plus the core coverage/role/sale boundary cases. This is not the wider release gate. Before a wider release, the proposal is ten matrix cases with three fresh generations each, using the same exact model digest, profile, options and bounded input selection. Record all attempts, including failures; do not discard an inconvenient run or silently select the best wording. The 30-run gate has not been executed.

For every attempt, record these independent layers:

1. Execution: installed model identity, completion, timeout, memory failure, HTTP failure, CPU-allocation observation and timings. A truncated response is not a semantic failure or a pass.
2. Syntax/schema: complete JSON, required fields, permitted categories, output bounds and no unexpected tools.
3. Citations: retained and supplied IDs, exact eligible finding citation sets, complete sale support and no duplicate packet use. Valid IDs alone do not establish entailment.
4. Meaning: each sentence's subject, direction, repeated roles, coverage state/count, time bounds, qualifier, amount implication and inference strength agree with its cited evidence and supplied finding. Review the overview and limitations as carefully as observations.
5. Readability: short connected English, clear uncertainty, no raw hashes/internal address labels, invented units, advice or unsupported significance judgments.

The proposed gate requires zero unsupported material claims and zero missing required qualifications across these attempts, alongside successful structural/citation validation. Report errors by layer and case, rather than one aggregate accuracy number that hides a coverage or selling error. Quality failures block acceptance even when the HTTP request succeeded. A pass establishes only performance on this small fixture set; it does not prove general accuracy, live provider completeness, production capacity, or future outputs. Any model/profile/context change requires rerunning affected cases and rechecking the retained real report.

Verified official model references on 2026-10-12. The smaller 2B alternatives have not been downloaded or benchmarked for this comparison. The proposed 30-attempt semantic regression gate remains unrun and unpassed.
